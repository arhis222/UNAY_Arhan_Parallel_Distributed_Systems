COMMUNICATION CHANNELS - SPECIFICATION DRAFT

Topic: Communication channels between tasks

1. Objective
--------------------------------------------------------------------------------
The goal is to define how tasks use Broker and Channel to establish a
connection and exchange bytes. This document describes their expected behavior.
The internal implementation will be addressed in the design stage.

For this first version, we consider one client task and one server task.
Handling several clients at the same time is outside the scope of this version.
The questions that still need discussion are listed in Section 3.

2. Main classes
--------------------------------------------------------------------------------
Broker
------
The Broker allows tasks to wait for connections and connect to other tasks.

Constructor Broker(String name):
    - Creates a broker identified by name.
    - The name must not be null or empty.

Method accept(int port):
    - Allows the server task to accept a connection on the specified port.
    - Returns the server-side Channel endpoint for the connection.
    - Only one task may wait for a connection on a given port of the same
      broker at a time.
    - An invalid port or a conflicting use of the port must cause an error.
    - The valid port range and the exact errors still need to be specified.

Method connect(String name, int port):
    - Requests a connection to the broker identified by name, on the given port.
    - Returns the client-side Channel endpoint when the connection succeeds.
    - If the broker cannot be found, the operation fails.
    - Each side can read and write through its own endpoint. Bytes written by
      the client are read by the server, and vice versa.
    - The two endpoints belong to one connection, not two separate connections.

Channel
-------
A Channel represents one endpoint of a bidirectional byte stream:

    clientChannel <--------------------> serverChannel

Method read(byte[] bytes, int offset, int length):
    - Reads bytes sent by the other task into the given array, starting at
      offset, without reading more than length bytes.
    - Returns the number of bytes read when data is received.
    - Bytes must be read in the order in which the other task wrote them.
    - A read does not necessarily correspond to a complete write. For example,
      the bytes representing "Hello" may be read as "He" followed by "llo".
    - Behavior when no data is available or the connection is closed remains
      an open question below.

Method write(byte[] bytes, int offset, int length):
    - Sends bytes from the given array, starting at offset, without writing
      more than length bytes.
    - Returns the number of bytes written.
    - Preserves the order of the bytes.
    - No new bytes may be sent through a disconnected endpoint.
    - Waiting behavior and partial writes still need to be clarified.

For both read() and write(), offset and length must describe a valid range
within a non-null array. Invalid arguments must be rejected. The exact errors
and the behavior for length equal to zero remain to be specified.

Method disconnect():
    - Closes this endpoint for further sending.
    - The effects on the other endpoint, pending operations, and unread bytes
      still need to be specified.

Method disconnected():
    - Returns true when this endpoint is disconnected, and false otherwise.
    - Whether a peer's disconnection changes this result is an open question.

Task
----
A Task extends Thread and executes the work that uses the communication layer.

Constructor Task(Broker b, Runnable r):
    - Creates a task associated with broker b and runnable r.
    - The broker is used by the task to establish connections.
    - The runnable defines the work performed by the task.
    - Creating the task does not start it. Calling start(), inherited from
      Thread, starts its execution and runs the supplied work in that thread.

Method static Broker getBroker():
    - In this proposed specification, returns the broker associated with the
      task making the call.
    - Different tasks may be associated with different brokers.
    - Behavior when called outside a Task remains to be specified.

Example: the tasks in an echo exchange

The client task connects, sends the bytes representing "Hello", and reads the
reply. The server task accepts the connection, reads the bytes, and sends the
same bytes back.

    Client Task                              Server Task
    calls:                                   calls:
    clientChannel.write(...)  ------------>  serverChannel.read(...)
    clientChannel.read(...)   <------------  serverChannel.write(...)

The tasks execute these calls. The Channel does not decide by itself to send a
message or produce a reply. Each task uses its own endpoint of the connection.

I think of the tasks as two people talking, the endpoints as their phones,
and the connection as the call. The broker helps establish the call.

3. Questions to discuss
--------------------------------------------------------------------------------
These questions concern observable behavior, so they should be settled in the
specification before implementing it.

Connection establishment:
    - Does accept() wait until a client connects before returning?
    - If connect() is called before accept(), does it wait or fail?
    - What port values are valid, and which errors should be reported?
    - Can the same port be reused after disconnection?
    - Must broker names be unique, and what happens if a name is already used?

Reading and writing:
    - Does read() wait when no bytes are available?
    - Can read() return as soon as some bytes are available, even if fewer
      than length bytes have arrived?
    - Does write() wait when it cannot make progress? Can it return after
      writing only part of the requested data?
    - What does read() return when the connection is closed and no data remains?
    - What happens if write() is called after disconnection?
    - Which exceptions are used for invalid arrays, offsets, and lengths?
    - Do zero-length reads and writes return 0 immediately?
    - Can both sides send at the same time (full-duplex communication)?

Disconnection and tasks:
    - Does disconnect() close communication in both directions?
    - Can bytes sent before disconnection still be read?
    - How do pending reads and writes finish after disconnection?
    - Are repeated calls to disconnect() harmless or errors?
    - What happens if a waiting task is interrupted?
    - What happens if getBroker() is called from a thread that is not a Task?
    - What happens if the Task constructor receives a null broker or runnable?

4. Notes for the next steps
--------------------------------------------------------------------------------
Echo-server test:
    - Establish a connection between the client and server tasks.
    - Send a known byte sequence and have the server echo it back.
    - Check that the reply has exactly the same bytes, length, and order.
    - Handle partial reads and writes if the final specification allows them.
    - Disconnect and check that both tasks terminate as expected.

Other cases to test once their behavior is specified:
    - Long transfers and repeated exchanges.
    - Reading when no data is available.
    - Writing when the operation cannot immediately make progress.
    - Disconnection during a read or write.
    - Invalid arguments and repeated disconnection.

This specification does not require the tasks to run in the same process or
on different machines. Data structures such as circular buffers belong to the
design stage; the behavior visible to the tasks belongs to the specification
as we discussed in the lesson.
